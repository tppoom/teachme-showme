index ทำให้ค้นเร็วขึ้นหลายร้อยเท่าได้อย่างไร

อธิบายได้ว่า index ทำงานอย่างไร รู้ว่า query แบบไหนใช้มันไม่ได้ และเช็กเองได้ว่าฐานข้อมูลใช้มันจริงหรือเปล่า

ตาราง orders มีหนึ่งล้านแถว คุณอยากได้ออเดอร์ทั้งหมดของลูกค้าหมายเลข 4821 คำสั่งนี้ใช้เวลาราว 50 มิลลิวินาที พอสร้าง index เพิ่มบรรทัดเดียว เวลาเหลือราว 0.1 มิลลิวินาที ข้อมูลเท่าเดิม คำสั่งเท่าเดิม อะไรเปลี่ยนไป

SELECT * FROM orders WHERE customer_id = 4821;

CREATE INDEX idx_orders_customer ON orders(customer_id);

ก่อนมี index ฐานข้อมูลไม่รู้เลยว่าแถวของลูกค้า 4821 อยู่ตรงไหน วิธีเดียวที่แน่ใจว่าไม่พลาดคือหยิบทุกแถวขึ้นมาดูทีละแถว ครบหนึ่งล้านครั้ง เหมือนหาชื่อเพื่อนในสมุดรายชื่อที่หน้ากระดาษถูกสลับมั่ว

สำเนาที่เรียงไว้ ทำให้ตัดทิ้งได้ทีละครึ่ง

index คือสำเนาของคอลัมน์ที่เรียงจากน้อยไปมาก แต่ละค่ามีตัวชี้กลับไปยังแถวจริงในตาราง ตัวตารางเองไม่ได้ถูกเรียงใหม่ ฐานข้อมูลเก็บสำเนานี้แยกไว้ และอัปเดตให้เองทุกครั้งที่ข้อมูลเปลี่ยน

หัวใจอยู่ที่คำว่าเรียง เพราะเมื่อค่าเรียงกันแล้ว การดูค่าตรงกลางเพียงครั้งเดียวก็บอกได้ว่าสิ่งที่หาอยู่ครึ่งไหน อีกครึ่งตัดทิ้งได้ทั้งหมดโดยไม่ต้องเปิดดู เหมือนเปิดพจนานุกรมหาคำว่า "แมว" แล้วเจอหมวด น ตรงกลางเล่ม คุณรู้ทันทีว่าต้องพลิกไปข้างหลัง

ตัวอย่าง — หา 4821 ในค่าที่เรียงแล้วตั้งแต่ 1 ถึง 1,000,000
  1. ดูค่ากลาง 500,000 มากกว่า 4821 จึงตัดครึ่งหลังทิ้ง เหลือห้าแสนค่า
  2. ดูค่ากลางของส่วนที่เหลือ 250,000 ยังมากกว่า เหลือสองแสนห้าหมื่นค่า
  3. ทำซ้ำไปเรื่อยๆ ทุกครั้งที่ดู ส่วนที่ต้องค้นจะหายไปครึ่งหนึ่ง
ดูราว 20 ครั้งก็เจอ เพราะหนึ่งล้านหารสองได้ราว 20 รอบก่อนจะเหลือค่าเดียว

สิ่งที่ทำให้ index คุ้มจริงๆ คือมันโตช้ามาก ทุกครั้งที่ข้อมูลเพิ่มเป็นสองเท่า การค้นต้องดูเพิ่มแค่หนึ่งครั้ง ข้อมูลโตขึ้นพันเท่า จึงดูเพิ่มเพียงราวสิบครั้ง ขณะที่การอ่านทุกแถวช้าลงพันเท่าตามข้อมูล

จำนวนแถวไม่มี indexมี index
1,000ดู 1,000 ครั้งราว 10 ครั้ง
1,000,000ดู 1,000,000 ครั้งราว 20 ครั้ง
1,000,000,000ดู 1,000,000,000 ครั้งราว 30 ครั้ง
ลงลึก: ทำไมฐานข้อมูลเก็บ index เป็น B-tree ไม่ใช่รายการที่เรียงไว้เฉยๆ

รายการที่เรียงไว้ค้นเร็วก็จริง แต่เพิ่มข้อมูลช้า เพราะการแทรกค่าใหม่ตรงกลางต้องเลื่อนทุกค่าที่อยู่ข้างหลังออกไป ฐานข้อมูลจึงแบ่งค่าที่เรียงแล้วเป็นก้อนเล็กๆ ก้อนละหลายร้อยค่า แล้วซ้อนก้อนพวกนี้เป็นชั้นๆ เรียกว่า B-tree

การค้นยังตัดทิ้งได้ทีละมากเหมือนเดิม แต่การแทรกค่าใหม่แก้แค่ก้อนเดียว และเพราะแต่ละก้อนมีหลายร้อยค่า ตารางหนึ่งล้านแถวจึงมี B-tree สูงแค่สามถึงสี่ชั้น

ไม่ต้องเดา ถามฐานข้อมูลได้เลย

ใส่ EXPLAIN QUERY PLAN นำหน้า query แล้ว SQLite จะบอกแผนที่มันจะใช้ก่อนรันจริง (PostgreSQL และ MySQL ใช้คำว่า EXPLAIN) คำแรกของผลลัพธ์คือสิ่งที่ต้องดู

ก่อนสร้าง index
EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE customer_id = 4821;
SCAN orders
หลังสร้าง index
EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE customer_id = 4821;
SEARCH orders USING INDEX idx_orders_customer (customer_id=?)

SCAN แปลว่าอ่านทุกแถว SEARCH … USING INDEX แปลว่ากระโดดไปหาค่าผ่าน index index ไม่ได้มาฟรี ทุกครั้งที่เพิ่มหรือแก้แถว ฐานข้อมูลต้องอัปเดต index ทุกตัวของตารางนั้นด้วย จึงสร้างเฉพาะคอลัมน์ที่ใช้ค้นบ่อยจริง

กับดัก: ครอบคอลัมน์ด้วยฟังก์ชันแล้ว index ใช้ไม่ได้

สมมติมี index บนคอลัมน์ email แล้ว แต่คุณอยากค้นโดยไม่สนตัวพิมพ์ใหญ่เล็ก จึงเขียน lower(email) แผนของ query กลับเป็นอ่านทุกแถวเหมือนไม่มี index

EXPLAIN QUERY PLAN SELECT * FROM orders WHERE email = 'nok@mail.com';
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE lower(email) = 'nok@mail.com';
SEARCH orders USING INDEX idx_orders_email (email=?) SCAN orders

เหตุผลอยู่ที่สิ่งที่ index เรียงไว้ มันเรียงตามค่า email ตามที่บันทึก ไม่ได้เรียงตามค่าหลังผ่าน lower() ฐานข้อมูลจึงตัดครึ่งไม่ได้ ต้องคำนวณ lower() ทีละแถวจนครบ ทางแก้คือบันทึก email เป็นตัวพิมพ์เล็กตั้งแต่แรก หรือสร้าง index บนตัวฟังก์ชันเลย CREATE INDEX … ON orders(lower(email)) ซึ่ง SQLite และ PostgreSQL รองรับ

จำไว้ข้อเดียว

query ช้าเมื่อไร ให้ดู EXPLAIN ก่อน ถ้าเห็น SCAN บนตารางใหญ่ แปลว่าฐานข้อมูลกำลังอ่านทุกแถว

ตาราง users มีหนึ่งล้านแถวและมี index บนคอลัมน์ phone เงื่อนไขไหนจะได้แผนแบบ SEARCH

เทียบค่าเต็มตรงๆ เงื่อนไขที่ใช้ค่าแบบเดียวกับที่ index เรียงไว้เท่านั้น ที่ให้ฐานข้อมูลตัดครึ่งได้

ตาราง orders โตจากหนึ่งล้านเป็นหนึ่งพันล้านแถว query ที่ใช้ index ต้องดูเพิ่มขึ้นราวเท่าไร
