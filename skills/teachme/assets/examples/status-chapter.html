Where the project stands

What is finished, what is half-built, what is broken, and which of those you are allowed to depend on today.

CoreOrientation
After this chapter you can
  • Say which subsystems are safe to build on and which will move under you
  • Find the evidence for every status claim here, yourself, in the repository
  • Name the two known-broken paths and pick a first task that will not collide with work in flight

Every other chapter explains how something works. This one explains how much of it is true right now — and the second question is the one that wastes weeks when nobody answers it. A newcomer who assumes the whole architecture is built will spend three days integrating with a module that has never run in production.

So one rule: no status claim without evidence you can check. Every line below points at a file, a test directory or a pull request. Written against commit a3f91c2, 14 January 2026; status ages in weeks, so when the evidence stops matching, trust the repository and fix this page.

Four states of "done"

A module can be fully written and fully tested and still be worthless to you, because nothing calls it. Most confusion here comes from collapsing these four into one word.

✅
Shipped
Running in production, covered by tests, handling real traffic. Safe to depend on.
🔌
Built, unwired
The code exists and its tests pass, but no caller reaches it. Works in isolation; unproven in the system.
🚧
Started
Someone is mid-flight. Interfaces will change without warning. Do not build on it; talk to them.
⬜
Not started
Named in the design, no code. Honest and harmless — as long as nobody assumes otherwise.

The dangerous one is the second. "Built, unwired" passes review and CI and shows green on every dashboard, then fails the first time real data touches it.

What is broken, and what comes next

Two known paths fail silently — no exception, no log — and look like your own mistake when you hit them. Both have open issues and neither has an owner.

🚫
Token refresh drops the request body

A POST that arrives with an expired token gets refreshed and retried — with an empty body. Silent: you get a 422 about missing required fields and go looking in entirely the wrong place.

auth/middleware.py:88 — issue #497. Workaround: refresh explicitly before any POST in a long-lived client.

🚫
The queue loses jobs on redeploy

In-flight jobs are not drained before shutdown. Roughly one job per deploy vanishes with no error anywhere — it simply never completes, and nothing logs it.

queue/worker.py:141 — issue #501, open since August. Anything that must not be lost has to be idempotent and re-driven from its own source of truth.

Exercise · Verify this chapter yourself

Do not take any of the above on trust. In a clean checkout, establish three things:

  1. Whether search/ really has no callers.
  2. How many tests tests/auth/ actually contains today.
  3. Whether PR #518 is still open.
Solution 
# 1 — does anything outside search/ import it?
grep -rn "from search\|import search" --include=*.py . | grep -v "^./search/\|^./tests/search/"

# 2 — how many auth tests are there really?
grep -rc "def test_" tests/auth/ | awk -F: '{n+=$2} END {print n}'

# 3 — is the indexer PR still open?
gh pr view 518 --json state,title,updatedAt

The first command returning nothing is the "built, unwired" claim, verified. If it returns something, search has been wired up since this was written and the chapter is out of date.

The habit matters more than the commands: a status claim you cannot reproduce in under a minute is a rumour.

In short

  • Four states, not two — and "built, unwired" is the trap: green tests, zero callers.
  • api/, auth/ and queue/ are safe to depend on. indexer/ is moving. search/ is unproven. billing/ does not exist.
  • Two known silent failures: #497 (refresh drops POST bodies) and #501 (redeploy loses jobs). Check every claim here — this page ages faster than the code.
Checkpoint

A module has 22 passing tests and full coverage. What does that tell you about depending on it?

Almost nothing alone. That is exactly the state search/ is in: self-consistent against fixtures, unproven against the system.

Your client POSTs to the API and gets a 422 about missing required fields, though the body is correct in your logs. The session token was issued an hour ago. What do you check first?

Token refresh drops the POST body (auth/middleware.py:88, #497). The 422 sends you hunting in the wrong place, which is why a known silent failure earns its own chapter.

You need a job that absolutely must not be lost. What does this chapter tell you to do?

Defend the job. The fix cannot be scheduled, so idempotency has to live in your code.

What one-word command distinguishes "built" from "wired in" faster than reading any code?

grep. Searching for imports and call sites answers "does anything actually use this?" in seconds — it is how the search/ gap was found.
