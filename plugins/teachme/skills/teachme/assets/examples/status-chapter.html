Where the project stands

What is finished, what is half-built, what is broken, and which of those you are allowed to depend on today.

CoreOrientation

Why this chapter exists

Every other chapter in this course explains how something works. This one explains how much of it is actually true right now. Those are different questions, and the second one is the one that wastes weeks when nobody answers it. A newcomer who reads an architecture document and assumes all of it is built will spend three days integrating with a module that has never run in production.

So this chapter has one rule: no status claim without evidence you can check. Every line below points at a file, a test directory, or a pull request. If you read this in six months and the evidence no longer matches, trust the repository and not this page — and then fix this page.

⚠️
This chapter has a shelf life

Written against commit a3f91c2, 14 January 2026. Architecture ages in years; status ages in weeks. Check the dates on the evidence before you rely on any of it.

The four states, and why three of them look alike

"Done" is not one thing, and most confusion on this project comes from collapsing four genuinely different states into it. A module can be fully written and fully tested and still be worthless to you, because nothing calls it.

✅
Shipped
Running in production, covered by tests, handling real traffic. Safe to depend on.
🔌
Built, unwired
The code exists and its tests pass, but no caller reaches it. Works in isolation; unproven in the system.
🚧
Started
Someone is mid-flight. Interfaces will change without warning. Do not build on it; talk to them.
⬜
Not started
Named in the design, no code. Honest and harmless — as long as nobody assumes otherwise.

The dangerous state is the second one. "Built, unwired" reads as finished in every code review, passes CI, and shows up green on any coverage dashboard — and then fails the first time real data touches it, because no real data ever has. Two of the subsystems below are in exactly that state.

The grep in the search row is worth running yourself rather than believing. It is the cheapest possible test of whether something is wired in, it takes two seconds, and it is how the "built, unwired" state was discovered in the first place — the module looked complete in every other respect.

What is known broken

Two paths fail in ways that will cost you an afternoon if you meet them without warning. Both are known, both have issues open, and neither has an owner.

🚫
Token refresh drops the request body

A POST that arrives with an expired token gets refreshed and retried — with an empty body. Silent: you get a 422 about missing required fields and go looking in entirely the wrong place.

auth/middleware.py:88 — issue #497. Workaround: refresh explicitly before any POST in a long-lived client.

🚫
The queue loses jobs on redeploy

In-flight jobs are not drained before shutdown. Roughly one job per deploy vanishes with no error anywhere — it simply never completes, and nothing logs it.

queue/worker.py:141 — issue #501, open since August. Anything that must not be lost has to be idempotent and re-driven from its own source of truth.

Both bugs share a shape worth internalising: they fail silently. Neither raises, neither logs an error, and both look like your own mistake when you hit them. That is why they belong in a chapter rather than an issue tracker nobody reads on day one.

Exercise · Verify this chapter yourself

Do not take any of the above on trust. In a clean checkout, establish three things:

  1. Whether search/ really has no callers.
  2. How many tests tests/auth/ actually contains today.
  3. Whether PR #518 is still open.
Solution 
# 1 — does anything outside search/ import it?
grep -rn "from search\|import search" --include=*.py . | grep -v "^./search/\|^./tests/search/"

# 2 — how many auth tests are there really?
grep -rc "def test_" tests/auth/ | awk -F: '{n+=$2} END {print n}'

# 3 — is the indexer PR still open?
gh pr view 518 --json state,title,updatedAt

The first command returning nothing is the whole "built, unwired" claim, verified in one line. If it now returns something, search has been wired up since this was written and this chapter is out of date — which is exactly the outcome the exercise is designed to catch.

The general habit matters more than these three commands: a status claim you cannot reproduce in under a minute is a rumour. Every row in the table above was written by running something like this, and every row should be re-checkable the same way.

Recap

  • Four states, not two: shipped, built-but-unwired, started, not started.
  • "Built, unwired" is the trap — green tests, zero callers, never met real data.
  • api/, auth/ and queue/ are safe to depend on. indexer/ is moving. search/ is unproven. billing/ does not exist.
  • Two known silent failures: #497 (refresh drops POST bodies) and #501 (redeploy loses jobs).
  • Every claim here is checkable in one command. Check it, because this page ages faster than the code.
Checkpoint

A module has 22 passing tests and full coverage. What does that tell you about whether you can depend on it?

Almost nothing alone. That is precisely the state search/ is in. Tests written against fixtures prove the module is self-consistent; they say nothing about whether anything calls it or whether real data has the shape the fixtures assumed.

You need to run a job that absolutely must not be lost. What does this chapter tell you to do?

Use the queue, and defend the job. "Shipped" means in production, not flawless. Issue #501 is open, unowned and silent, so the defence has to live in your job rather than in a fix you cannot schedule.

What one-word command distinguishes "built" from "wired in" faster than reading any code?

grep. Searching for imports and call sites answers "does anything actually use this?" in seconds. It is the cheapest status check there is, and it is how the search/ gap was found.
