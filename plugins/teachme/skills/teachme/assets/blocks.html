The channel is created

Unbuffered, so a send blocks until a receiver is ready. Nothing runs concurrently yet.

The goroutine is scheduled

go returns immediately. worker has not necessarily started — the scheduler decides. This is the line people misread.

main blocks on the receive

The runtime parks main and runs worker on the freed thread.

var wg sync.WaitGroup

Best when you only need to know that everyone finished.

g, ctx := errgroup.WithContext(ctx)

Best when any worker can fail and you want the first error.

✍️Try it yourself

Start three goroutines that print 1, 2, 3 and make main wait for all of them.

Show the solution 
var wg sync.WaitGroup
for i := 1; i <= 3; i++ {
    wg.Add(1)
    go func(n int) { defer wg.Done(); fmt.Println(n) }(i)
}
wg.Wait()

Why: wg.Add runs before the go statement so the counter can never reach zero early. The numbers print in any order — that is correct.

Recap

  • A goroutine is a runtime-scheduled function, not an OS thread.
  • main returning kills every goroutine still running.

What happens to running goroutines when main returns?

Why: the process exits when main returns; nothing waits. The first option is tempting because that is how thread joins work in most languages — Go makes you ask for it with sync.WaitGroup or a channel.
